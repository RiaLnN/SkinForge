# osu-mixer — сборка, проверка, и план на GUI (Этап 4)

Этот документ — про то, как собрать и проверить всё написанное на Этапах 1-3
у себя на машине, и рекомендации по архитектуре GUI на `egui`/`eframe` для
Этапа 4. Кода GUI здесь нет намеренно — только советы по структуре, чтобы вы
писали его сами (или чтобы я писал по вашим уточнениям отдельно).

---

## 1. Сборка и проверка того, что уже есть

### 1.1 Предпосылки

- **.NET SDK 8+** — для `realm-bridge`. Проверить: `dotnet --version`.
- **Rust** — рекомендую ставить через `rustup`, а не через системный
  пакетный менеджер. В песочнице, где писался этот код, был доступен только
  `rustc 1.75` из `apt`, из-за чего пришлось точечно фиксировать версии
  нескольких крейтов (`sysinfo`, `clap`, `uuid`, `zip` — см. комментарии в
  `Cargo.toml`). На вашей машине с актуальным `rustup` (stable, обычно
  1.80+) эти пины можно и стоит снять — `cargo update` подтянет свежие
  версии без изменений в коде.
- Для GUI дополнительно проверьте версию Rust заранее: `egui`/`eframe`
  довольно активно поднимают MSRV между релизами. Если после `cargo add
  eframe` сборка ругается на версию языка — либо обновите `rustup`
  (`rustup update stable`), либо явно зафиксируйте более старую версию
  `eframe`/`egui` в `Cargo.toml` (`cargo add eframe@0.27` и т.п., подобрав
  версию под ваш тулчейн методом `cargo build` → смотрим на ошибку → правим).

### 1.2 Сборка `realm-bridge` (C#)

```bash
cd realm-bridge
dotnet restore
dotnet build -c Release
```

Если что-то не собралось — скорее всего 1-2 вызова Dynamic API в
`RealmOperations.cs`, помеченные комментарием `NOTE` (сигнатуры
`DynamicApi.CreateEmbeddedObjectForProperty`/`CreateObject`/`Find` немного
отличаются между версиями пакета `Realm`; вы уже собирали на 20.1.0 и
`dump-skins` работал — если пересобираете на другой машине с другой версией
пакета, эти места — первое, куда смотреть при ошибках компиляции).

Для конечной раздачи — self-contained + AOT, чтобы не требовать у
пользователя установленного .NET:

```bash
dotnet publish -c Release -r linux-x64 --self-contained true -p:PublishAot=true
dotnet publish -c Release -r win-x64   --self-contained true -p:PublishAot=true
```

### 1.3 Сборка и тесты `osu-mixer-core` (Rust)

```bash
cd osu-mixer-core
cargo build
cargo test
```

Ожидается 26 зелёных тестов (`skin_ini`, `osk`, `categorize`, `mixer`,
`storage`, `bridge`, `paths`, `process_guard`).

### 1.4 Чек-лист ручной проверки CLI (сквозной прогон)

Полезно повторить после любых изменений в `mixer.rs`/`categorize.rs` — это
тот же сценарий, что гонялся при разработке Этапа 3:

1. Собрать тестовый `.osk` (обычный zip) с `skin.ini` и парой ресурсов —
   либо вручную (`zip -r Donor.osk .` из папки скина), либо взять любой
   реальный скин-донор.
2. `cargo run -- inspect-donor Donor.osk --extract-to <tmp>` — проверить,
   что имя/автор/комбо-цвета из `skin.ini` распознались верно и файлы легли
   в ожидаемые категории (особенно: numbered-файлы типа `default-N`/`sliderb0`,
   звуки с sampleset-префиксом `normal-`/`soft-`/`drum-`).
3. `cargo run -- build-patch Donor.osk --files-dir <tmp>/files --base-skin-id
   <guid-существующего-скина> --name "..." --creator "..." --out patch.json`
   — проверить, что `patch.json` содержит один `duplicate_skin` + по одному
   `add_file` на файл, и что файлы физически появились в
   `<tmp>/files/x/xy/<hash>`.
4. `cargo run -- dump-skins --bridge-binary <path> --db <path/к/client.realm
   .bak-копии, НЕ к боевой базе>` — сверить, что мост в принципе жив на
   вашей машине.
5. `cargo run -- apply-mix ...` — **только на копии базы** (`.bak`), не на
   боевой `client.realm`, пока не уверены в поведении на конкретной версии
   схемы lazer. Проверить, что скин реально появился при следующем
   `dump-skins`.

### 1.5 Структура workspace под GUI

Рекомендую превратить репозиторий в Cargo workspace из двух членов:

```
Cargo.toml            # [workspace] members = ["osu-mixer-core", "osu-mixer-gui"]
osu-mixer-core/        # уже есть — lib + CLI, без изменений
osu-mixer-gui/          # новый bin-крейт, egui/eframe, зависит от osu-mixer-core как path-зависимости
realm-bridge/            # C#, вне workspace (свой .csproj)
```

Так GUI не дублирует логику, а полностью переиспользует `paths`,
`process_guard`, `storage`, `bridge`, `skin_ini`, `osk`, `categorize`,
`mixer` — весь код, который уже собран и протестирован на Этапах 1-3.

### 1.6 Как проверять GUI, когда он появится

GUI с реальным окном нельзя прогнать в headless-песочнице (нет дисплея), так
что план проверки такой:

- **Бизнес-логику — юнит-тестами**, отдельно от отрисовки (см. раздел 2.6
  ниже про разделение слоёв). Она гоняется в CI/песочнице так же, как
  `osu-mixer-core` сейчас.
- **Отрисовку и интерактив — руками, у вас**, через `cargo run -p
  osu-mixer-gui`. Не пытайтесь заранее верить, что виджет выглядит как
  задумано — egui нередко удивляет раскладкой, особенно в первый раз.
- Если хочется автоматизированных проверок именно UI-слоя — присмотритесь к
  крейту `egui_kittest` (снапшот-тестирование egui-виджетов без реального
  окна, есть headless-рендер через `wgpu`); это не обязательно для рабочего
  прототипа, но полезно, если UI будет обрастать регрессиями.

## 2. Рекомендации по архитектуре GUI (без кода — только советы)

### 2.1 Главный принцип: GUI — тонкий, логика — в `osu-mixer-core`

Всё, что можно проверить юнит-тестом без окна (какой файл в какую категорию
попал, какие операции войдут в патч, какой хэш у файла), уже лежит в
`osu-mixer-core` и должно там и оставаться. `osu-mixer-gui` — это слой,
который: (а) вызывает функции ядра, (б) держит состояние выбора пользователя,
(в) рисует. Если в процессе написания GUI обнаружится, что какая-то логика
удобнее прямо во view-коде — это сигнал вынести её обратно в `mixer.rs` и
покрыть тестом, а не оставлять в отрисовке.

### 2.2 Важный архитектурный нюанс: цвета — это тоже файл

В исходном плане вкладка "Цвета" выглядит как отдельная категория наравне с
Gameplay/Cursor/Audio/Interface, но технически комбо-цвета — не отдельное
поле в базе Realm, а часть текста `skin.ini`, который сам является одним из
`Files` скина (обычным content-addressed ресурсом, как и любой `.png`).
Значит редактирование цветов не требует нового типа операции патча — это тот
же `add_file`, что и для спрайта: вы генерируете новый текст `skin.ini`
(меняете строки `ComboN:` через уже написанный `skin_ini.rs`-парсер — его
стоит дополнить сериализацией обратно в текст, раз он сейчас только читает),
хэшируете и кладёте через `storage::store_resource`, а `add_file` нацеливаете
на имя `skin.ini`. Стоит явно заложить это в модель состояния GUI: вкладка
"Цвета" не хранит выбор файла-донора, а хранит отредактированные значения
`ComboN`, которые в момент сборки патча превращаются в сгенерированный
`skin.ini`.

### 2.3 Состояние приложения и потоки

`realm-bridge` вызывается как внешний процесс — даже на быстрой машине это
десятки-сотни мс на старт .NET, а хэширование крупных `.wav`/`.mp3` тоже не
мгновенно. Не вызывайте `RealmBridge`/`storage::store_resource` синхронно в
`update()` — весь UI встанет колом на время операции. Стандартный паттерн для
`eframe`: держать в состоянии приложения канал (`std::sync::mpsc` или
`crossbeam-channel`), запускать операцию в `std::thread::spawn`, а
`update()` на каждый кадр не блокируясь проверять канал (`try_recv`) на
результат. Прогресс-бар/модалку показывайте, пока флаг "операция идёт" не
снят пришедшим по каналу результатом; `ctx.request_repaint()` дёрните сразу
после отправки задачи в фоновый поток, чтобы UI не ждал следующего
пользовательского ввода для перерисовки.

Единственное состояние, которое обязано жить в `eframe::App` и не может
уехать в чистые функции — собственно виджеты (текстуры, `rodio::Sink`).

### 2.4 Текстуры и превью

Декодирование PNG (крейт `image`) — делайте в фоновом потоке (том же, что
хэширует/копирует, или отдельном), а `Context::load_texture` — только на
UI-потоке (это требование `egui`). Практический паттерн: фоновый поток
декодирует байты в `egui::ColorImage` и отправляет его по каналу; `update()`
на UI-потоке получает и только там вызывает `load_texture`. Кэшируйте
текстуры по хэшу файла (`HashMap<String /* sha256 */, TextureHandle>`), а не
по имени файла — тогда одинаковый по содержимому спрайт из разных доноров
не грузится и не держится в памяти повторно, это прямое продолжение
дедупликации, которая уже есть в `storage.rs`.

Для "мини-сцены" превью (нота + `approachcircle` + курсор с трейлом) проще и
надёжнее не городить послойную композицию через `egui::Painter` каждый кадр,
а один раз (при смене выбора) отрендерить композит через сам крейт `image`
(наложение слоёв с альфа-блендингом в оффскрин-буфер) и показать как одну
текстуру. Дороже при каждой смене выбора, зато дёшево на кадр и не тащит
логику позиционирования слоёв в код отрисовки. Анимацию (наезжающий
`approachcircle`) можно добавить отдельным слоем поверх статичного композита
через `ctx.request_repaint_after` — это чисто косметика, не обязательна для
рабочей версии.

### 2.5 Аудио

`rodio::Sink` нужно держать в состоянии приложения, а не создавать заново на
каждый клик — если `Sink` дропнется, звук оборвётся. Байты файла для
предпрослушки стоит читать один раз при выборе (или при первом клике,
лениво) и кэшировать в памяти — то же самое "не дёргать диск на каждый
клик", что и для текстур.

### 2.6 Разделение слоёв — чтобы логику можно было тестировать

Держите структуру состояния (какие файлы выбраны для замены, значения
цветов, какой донор активен) в обычных Rust-структурах без прямой зависимости
от `egui`, а функции, которые эти структуры меняют по действию пользователя
("выбрали файл X для слота Y", "переключили категорию") — как чистые функции
`State + Action -> State`, отдельно от кода отрисовки. Тогда переходы
состояния (в том числе то, что в итоге попадёт в `MixPlan`/
`Vec<ReplacementSelection>`) можно юнит-тестировать без дисплея, а
`update()` останется тонким переводчиком "клик по кнопке → вызов функции
перехода состояния → отрисовка текущего состояния".

### 2.7 Поддержка нескольких доноров одновременно

Формулировка задачи допускает смешивание элементов из разных
скинов-доноров ("курсор — из одного, хитсаунды — из другого"). Стоит сразу
проектировать состояние как реестр загруженных доноров
(`Vec<DonorSkin>`, уже возвращается `mixer::load_donor()`), а выбор —
как отображение "имя файла в целевом скине → (индекс донора, имя файла у
донора)", а не как состояние одного активного донора. Переключение вкладки
"какой донор сейчас смотрим" в сайдбаре не должно сбрасывать уже сделанные
выборы из других доноров.

### 2.8 Диалоги выбора файла/папки

Для кнопки "Импортировать скин-донор" (и .osk-файл, и папка — оба валидных
входа для уже написанного `resolve_donor_root`/`mixer::load_donor`)
понадобится нативный диалог выбора. Кросс-платформенный стандарт в
экосистеме `egui`/`eframe` — крейт `rfd` (`pick_file`/`pick_folder`). Он не
входит в `eframe` по умолчанию, добавляется отдельно.

### 2.9 Сетка выбора компонентов

Для грида превью внутри категории — `egui::Grid` для простой раскладки
фиксированной ширины или `egui_extras::TableBuilder`, если понадобится
скролл с виртуализацией на скинах с сотнями файлов (актуально для
Interface/Gameplay категорий с полными наборами `default-0..9`,
`ranking-*` и т.п.). Виртуализация важна, если рендерить текстуру на каждую
ячейку без неё — лишняя нагрузка на сотни виджетов одновременно.

### 2.10 Экран сохранения и прогресс

Модалку "Собрать и применить" реализуйте как полноэкранный полупрозрачный
`Area`/`Window` поверх остального интерфейса, блокирующий клики по фону,
пока фоновый поток (см. 2.3) не пришлёт результат `apply_patch()`. Ошибки из
`CoreError` уже читаемые (`Display` реализован по-русски в `error.rs`) —
можно показывать текст ошибки как есть, без дополнительного маппинга. Если
хочется технических деталей для отладки — прячьте `Debug`-представление под
раскрывающийся блок, а не показывайте по умолчанию.

### 2.11 Порядок реализации, если делать поэтапно и внутри самого Этапа 4

Предлагаю не пытаться сразу собрать весь экран целиком, а идти так:
1. Список скинов в сайдбаре (просто вызов `dump_skins`, без интерактива) —
   проверяет, что интеграция с ядром и потоковая модель вообще работают.
2. Импорт донора + вкладки категорий с текстовым списком файлов (без превью)
   — проверяет `load_donor`/категоризацию в UI.
3. Добавить превью-текстуры в грид.
4. Добавить аудио-плеер.
5. Экран сохранения + реальный вызов `apply-mix` — сначала на тестовой копии
   базы, как и в CLI-чеклисте выше.

Так на каждом шаге есть рабочая (пусть и урезанная) версия, которую можно
руками проверить, вместо одного большого куска кода, который либо весь
работает, либо непонятно, где сломалось.
